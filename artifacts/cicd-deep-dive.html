CI/CD 深度導讀：從 P4 Changelist 到 Agentic Workflow

寫給在 EDA 軟體公司擔任 PE、有 check-in 權限、常替 QA 建 regression case 的你。目標不是背名詞，而是讓你看懂「一個成熟的系統，為什麼長成這樣」。

0學習地圖：CI/CD 到底在解決什麼？

一句話：讓「很多人同時改同一份程式碼」這件事，變得安全、快速、可追溯。

CI — Continuous Integration

每個改動都頻繁併回主線，且每次併入都自動 build + test。核心是「早點發現衝突與錯誤」，而不是「有一台 Jenkins」。

CD — Continuous Delivery

主線隨時處於可發佈狀態。要不要真的發，是商業決定（EDA 通常是季度 release + hotfix）。

CD — Continuous Deployment

每個通過測試的改動自動上線。網路服務常見；EDA 這種裝在客戶機器上的軟體幾乎不會這樣做。

心智模型：品質關卡（gate）漏斗越早的關卡越便宜、越快、越粗；越晚的越貴、越慢、越完整。成熟系統的設計藝術，就是決定「哪個測試放在哪個關卡」。

P4 與 Git 最本質的差異（為什麼 EDA 愛用 P4）

Perforce：集中式

伺服器是唯一真相；適合巨大 repo、大型二進位檔（testcase、GDS/OASIS、library、golden 結果）。檔案可以 lock。CL 編號是全域遞增的，天然有順序。

Git：分散式

每人有完整歷史；branch 極便宜，所以「一個 PR = 一個 branch」的文化很自然。大型二進位檔需要 LFS。GitHub 生態的自動化（Actions、agent）最豐富。

好消息：概念完全通用。Shelved CL + Swarm review + 觸發測試，就是 PR + required checks。你學會一邊，另一邊只是換名字。

2什麼是一個 PR？它的生命週期

PR（Pull Request）不是「一段程式碼」，而是一個協作物件：程式碼差異 + 說明 + 自動檢查結果 + 討論 + 核准紀錄。它是整個 CI/CD 的「工作單位」。

一個好 PR 的解剖

① Title

router: fix crash when via stack exceeds 12 layers (STAR-48213) — 模組＋做了什麼＋單號。

② Description

Why（問題/動機）、What（改了什麼）、How tested（跑了哪些測試、新增哪個 regression case）、Risk（影響範圍、QoR 是否變動）。

③ Diff

實際的程式碼變更。越小、越專注，review 品質越高。

④ Checks

CI 自動貼回來的結果：build ✔、lint ✔、smoke ✔、targeted regression ✔。

⑤ Review & Approval

誰看過、誰核准（Code Owner 規則：改 router 目錄就必須有 router owner 核准）。

⑥ Merge record

何時、由誰／哪個 queue 併入。之後出事可以 blame／revert。

狀態機

對照你的 P4：Shelve＝Open；Swarm 的 Needs Review / Needs Revision / Approved＝In Review / Changes requested / Approved；Submit＝Merged。Merge queue 在 P4 世界較少見，常被「submit 前再跑一次 PCA」或「submit 後 nightly 抓 regression」取代。

3CI/CD 全景：傳統流程 vs 目前主流

  • Build master / release engineer 手動處理合併與打包。
  • 「壞掉的 nightly」需要人去 bisect（二分搜尋）找出是哪個 CL。
  • 測試主要靠 QA 階段，開發者的回饋迴圈很長。
  • Trunk-based development：大家都往 main 小步快跑，branch 存活很短。
  • Required status checks：沒過就按不了 merge（你的 PCA 就是這個角色）。
  • Merge queue：解決「A 和 B 各自都綠，但一起進去就紅」— queue 會把 PR 依序和最新 main 一起再測一次。
  • 自動 bisect / culprit finder：post-submit 紅了，系統自動找出是哪個 CL 並建議 revert。
  • Pipeline as code：CI 設定（Jenkinsfile、.github/workflows/*.yml）也進版控、也要 review。

現代流程的骨架不變，但每個關卡旁邊多了 agent：

  • Issue／STAR 進來 → agent 自動重現、分類、找相關程式碼。
  • Agent 自己開 PR（GitHub Copilot coding agent、Claude Code、Codex 等都能從 issue 直接產生 PR）。
  • AI reviewer 在人類之前先過一輪（風格、明顯 bug、缺測試）。
  • CI 紅了 → triage agent 讀 log，判斷是 flaky、infra 問題還是真 bug，甚至直接推修正 commit。
新的瓶頸：人類 review 頻寬agent 產生 PR 的速度遠高於人類審查速度。因此 2025 年後成熟團隊的重心是：PR 要更小、測試要更強（測試才是 agent 的護欄）、核准權嚴格保留給人。

EDA 跟網路公司最大的不同，決定了你們流程的形狀：

特性對 CI/CD 的影響
單一 regression 可能跑數小時、吃大量 license 與機器不可能每個 CL 都跑全套 → 分層測試：pre-submit 只跑 smoke + 受影響模組；全套留給 nightly/weekly
結果是數值型（QoR：timing、area、power、runtime、DRC count）而非 pass/fail需要「容忍範圍」與趨勢圖；QoR 退步 0.3% 算不算 fail？這是人的判斷
Testcase 常來自客戶設計，有 NDA 限制測試資料權限控管；agent 能不能讀客戶資料是重大治理問題
軟體裝在客戶端、版本週期長是 Continuous Delivery 不是 Deployment；hotfix 需要 backport 到多個 release stream
非決定性（多執行緒、浮點）flaky test 多 → 需要 rerun 策略與 flaky 隔離機制

4Try job 是什麼？權限在哪裡？

Try job（try run／trybot）＝在程式碼「還沒進主線」之前，把你的改動丟到 CI 的機器上跑測試。Chromium 把這叫 tryjob；它們的 Commit Queue（CQ）有「dry run」（只測不併）與「full run」（測完自動併）兩種。

為什麼 try job 需要權限？

💰 成本

EDA regression 吃 license 和 farm 機器。任何人都能任意觸發全套 regression，排程會被塞爆。

🔐 安全

Try job＝在公司機器上執行未經 review 的程式碼。若 CI 環境能讀到客戶 testcase、密鑰、license server，就是資料外洩風險。

🧭 責任

能觸發「full run → 自動併入」的人，等於擁有 commit 權。這必須跟 code owner / committer 身份綁定。

關鍵原則：Agent 可以「提出」與「測試」，不可以「核准」自己的東西這就是職責分離（separation of duties）。GitHub 的 Copilot coding agent 也是這樣設計：它開的 PR 必須由另一個人核准，觸發 CI workflow 也預設需要人按下同意。

5一個 PR 該放多少東西？

你問的「每個小功能一個 PR，還是一個 PR 包很多功能」，業界答案相當一致：一個 PR ＝ 一個「邏輯上不可再切」的改動，不是「一個功能」也不是「一天的工作量」。

✅ 小 PR 的好處

review 更仔細（研究顯示超過約 400 行，reviewer 找 bug 的能力明顯下降）；出事可以單獨 revert；bisect 精準；衝突少；對 agent 來說 context 也更乾淨。

⚠️ 小過頭的代價

一堆互相依賴的 PR 拆得零碎，reviewer 看不到全貌；每個 PR 都要排 CI、等 review，等待時間累加。EDA 裡 regression 很貴時，拆太細會塞爆 farm。

判斷流程

經驗法則（EDA 版）

  • 新增 regression testcase 本身可以是獨立 CL：先提交「會重現 bug 的 testcase（標成 expected-fail）」，再提交修正並翻轉成 expected-pass。這讓 QA 和 reviewer 一眼看出「修正確實有效」。
  • Golden / QoR baseline 更新要獨立：不要把「改演算法」和「更新 400 個 golden 檔」混在一起，否則 reviewer 無法分辨哪些差異是預期的。
  • 機械性的大改動（全域改名、格式化、升級 compiler flag）：行數很大沒關係，但不能夾帶任何邏輯改動，並在描述中寫明怎麼產生的（指令或 script），reviewer 只需驗證流程。
  • 大致目標：人類寫的邏輯改動 < 200–400 行、reviewer 能在 30–60 分鐘內看完。

6公司怎麼用 PR 算工程師的貢獻？合理嗎？

誠實的答案：幾乎所有「可以直接數的東西」都可以被刷。這就是 Goodhart's Law：「當一個指標變成目標，它就不再是好指標。」

常見算法量到了什麼怎麼被刷 / 盲點合理性
PR / CL 數量活動量把一個改動拆成 10 個；修 typo 也算一個僅作參考
程式碼行數（LOC）打字量複製貼上、不重構；刪掉 2000 行爛 code 的人反而「負貢獻」；agent 一天能產生上萬行不合理
Review 數量 / 留言數協作參與LGTM 秒按；留無意義留言需看品質
修掉的 STAR / bug 數產出挑簡單的修；不同 bug 難度差百倍需加權
DORA 指標（部署頻率、變更前置時間、變更失敗率、恢復時間）團隊交付效能設計上是團隊層級，拿來比個人會失真團隊層級合理
SPACE 框架（滿意度、績效、活動、溝通協作、效率）多維度需要問卷與質化資料，成本高較完整
影響力敘事（impact）：解決了哪些客戶問題、帶來什麼 QoR、預防了多少 escape真實價值主觀、依賴主管理解技術最接近真相

小模擬：兩位工程師，誰貢獻大？

切換不同的「考核指標」，看排名怎麼翻轉。

工程師 A「勤奮型」

一季 48 個 PR，多是小修小補與格式調整，+12,000 行。用 agent 大量產生程式碼，review 草率。

工程師 B「深潛型」

一季 9 個 PR，其中一個重寫 timing cache，−3,000 行，修好 3 家大客戶的 runtime 問題，並補了 25 個 regression case。

比較合理的做法① 活動指標（PR 數、review 數）只用來發現異常（例如某人兩個月沒 review 任何人），不用來排名。② 團隊層級看 DORA。③ 個人層級看影響力 + 品質（例如 escape defect、你建的 regression case 抓到了幾次問題）。④ 把 review 別人、建 testcase、修 flaky 這些「隱形工作」明確算進去 — 這對 PE 角色尤其重要。
Agent 時代的新問題當 agent 能一小時開 20 個 PR，「PR 數」徹底失去意義。新的問題變成：誰為這個 PR 的正確性負責？多數公司的答案是「按下核准與 submit 的那個人」。因此你的價值會越來越體現在：定義問題、設計測試、判斷結果，而不是打字。

8軟體工程的 Agent 分工：最少需要哪些？

別被「十幾種 agent」的行銷圖嚇到。最小可行編制是 4 個角色，每個角色對應一個傳統流程中的關卡；第 5、6 個是成熟後再加。

① Coder / Implementer agent

輸入：STAR 內容、重現步驟、相關 log、程式碼庫。
做什麼：先重現問題 → 定位程式碼 → 寫修正 → 在本機/sandbox 跑相關測試 → shelve CL 或開 PR，並寫好 description。
權限：可讀 repo、可在 sandbox 執行、可 shelve／開 PR。不可 submit、不可改 CI 設定、不可改 golden。
產品例：Claude Code、GitHub Copilot coding agent、OpenAI Codex、Cursor background agent。

常見失敗模式「修症狀不修病因」（例如加個 null check 讓 crash 消失）、為了讓測試過而改測試。對策：要求 description 說明 root cause；Test agent 與 Coder 分開。

② Test / Regression agent

做什麼：(a) 把 bug 轉成最小化的 regression testcase（這正是你現在手動做的工作）；(b) 根據 diff 做測試選擇（test impact analysis）：這個 CL 改了 router，就挑 router 相關的 200 個 case 跑，而不是全部 5 萬個；(c) 比較 QoR 結果並產出差異報告。
權限：可新增 testcase（作為 PR 的一部分，需 review）；不可自行更新 golden。

為什麼要和 Coder 分開？同一個 agent 同時寫程式和寫測試，就像學生自己出考題給自己考。分開（不同 prompt、甚至不同模型）能形成互相制衡。

③ Reviewer agent

做什麼：在人類之前審 diff：邏輯錯誤、邊界條件、記憶體/執行緒問題、是否缺測試、description 是否和 diff 一致、是否碰到敏感檔案。只回報高信心問題，避免洗版。
權限：只能留言、標記 risk 等級；永遠不能 approve。
價值：讓人類 reviewer 專注在「設計對不對、需求對不對」，而不是抓 typo。

④ CI Triage / Build-doctor agent

做什麼：CI 紅了之後讀 log，分類成：infra（license 不夠、機器掛了）flaky（重跑就過）真 regression。真 regression 就做 bisect 找出罪魁 CL、通知作者、草擬 revert。
為什麼是最小編制之一：在 EDA 的大型 regression 裡，人每天花在「看哪裡紅了、為什麼紅」的時間非常可觀，這是 ROI 最高的自動化點之一。

⑤ Planner / Spec agent（成熟後加）

把模糊的 STAR 轉成結構化規格與驗收條件，拆成多個小任務（對應多個小 PR）。產出必須由人確認— 這是最上游的人類關卡。

⑥ Release / Docs agent

彙整 release notes、檢查 backport 清單、產生客戶可見的變更說明。

橫向：Orchestrator

負責分派、追蹤狀態、控制預算（避免 agent 無限重跑昂貴的 regression）。可以是一個 agent，也可以就是 CI 系統本身＋規則。

9實戰案例：一張 STAR 的一生

情境：客戶回報「Placement 後跑 router，在某個 12 層金屬的設計上 crash」。我們逐步走過一個成熟、半 agentic 的流程。點左邊每一步，看是誰、做什麼、用什麼工具、關卡在哪。

    10給 PE 的你：明天就能做的事

    回公司問這 8 個問題（答得出來，你就真的懂你們的系統了）

    1. PCA / pre-submit 測試具體跑哪些 case？誰決定這個清單？多久更新一次？
    2. Shelved CL 能不能觸發 regression？誰有權限觸發多大規模的？配額怎麼算？
    3. Submit 後的 nightly 紅了，誰負責 triage？有沒有自動 bisect？
    4. Golden / baseline 更新的流程是什麼？需要誰核准？
    5. Swarm 的 review 規則：需要幾個人 approve？有沒有 code owner 概念？
    6. Flaky test 怎麼處理？有沒有隔離（quarantine）清單？
    7. Hotfix 怎麼 integrate 到各個 release stream？誰決定要不要 backport？
    8. 目前導入的 agent 有哪些權限？它的 CL 誰來 review、誰負責？

    你的 regression case 品質清單

    ✔ 最小化

    能重現問題的最小設計／最少步驟，執行時間越短越好（越短越有機會進 pre-submit）。

    ✔ 斷言明確

    檢查什麼？不 crash？DRC = 0？timing slack ≥ X？「跑完沒報錯」是最弱的斷言。

    ✔ 決定性

    固定 seed、固定 thread 數，避免變成 flaky。

    ✔ 可追溯

    case 名稱或 metadata 裡帶 STAR 號碼，未來有人看到它失敗時知道它在保護什麼。

    ✔ 資料合規

    客戶設計是否可以進 regression？是否需要去識別化（obfuscate）？

    ✔ 分層標記

    標記為 smoke / sanity / full / QoR，讓 CI 知道這個 case 屬於哪一層關卡。

    11自我測驗

    先自己想，再點開。答不出來的，回去看對應章節。

    Q1. Pre-submit 和 post-submit 測試，為什麼不全部放在 pre-submit 就好？成本與延遲。若每個 CL 都要跑 6 小時的全套 regression，開發者回饋迴圈變成一天，大家會開始把改動攢成大 CL，反而違反 CI 精神。正確做法是分層：pre-submit 快速且高訊號，post-submit 完整並自動 bisect。
    Q2. A 和 B 兩個 CL 各自的 try job 都綠，submit 後 main 卻紅了，為什麼？如何預防？兩者在測試時都是基於「舊的 main」，沒有測到彼此的組合（semantic conflict）。預防：merge queue（依序和最新 main 一起測）、或 submit 前 rebase 後再跑一次必過測試。
    Q3. 一個 PR 同時「重新命名 200 個函式」和「修一個 timing bug」，有什麼問題？reviewer 無法在 200 處機械改動中找出真正的邏輯改動；若 bug 修錯要 revert，會連重新命名一起 revert。應拆成兩個：先純改名（regression 結果應完全一致），再修 bug。
    Q4. Agent 修完 bug，並且「順便」更新了 37 個 golden 檔讓 regression 全綠。你該怎麼看？高度警戒。這可能是真的預期變化，也可能是 agent 把錯誤結果寫成新的標準答案。golden 更新必須獨立成 CL，附 QoR 差異報告，由懂該模組的人核准。
    Q5. 主管想用「每季 PR 數」排名工程師，你會怎麼建議？PR 數可以當作異常偵測（完全沒產出、完全沒 review），但不適合排名：易被拆分灌水、無法反映難度與影響，agent 時代更是失真。建議團隊層級用 DORA，個人層級用影響力敘事 + 品質指標（escape defects、testcase 抓到的問題、review 貢獻）。
    Q6. 最小 agent 編制中，為什麼 Test agent 要跟 Coder agent 分開？避免「自己出題自己考」。測試是 agent 的護欄；同一個 agent 寫程式又寫測試，容易兩邊一起錯，或為了過關修改測試。
