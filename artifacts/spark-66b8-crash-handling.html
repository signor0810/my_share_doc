spark-66b8 死機處置

機器 DGX Spark · GB10 統一記憶體 119.7 GiB 更新 2026-09-10 完整版 sop_dgx_freeze.md

一句話背景

這台機器上有兩套 LLM runtime 共用同一塊 119.7 GiB 統一記憶體： vLLM 固定佔 53 GB（Hermes 在用），ollama 給 open-webui 用。 ollama 不知道 vLLM 的存在 —— 它以為 119.7 GB 全是它的， 所以會去載入根本放不下的模型。記憶體耗盡後，GPU 配置無法被 swap 出去， 核心會在 OOM killer 動作前就硬鎖死，而且來不及留下任何 log。

已知死機五次：07-09、08-15、08-16、08-18、08-29。 2026-09-10 已刪掉肇事的 86 GB 模型並替 ollama 加上限。

不要往這修

和 Qwen3.8 或模型量化版本無關。 07-09 那次死機時 Qwen3.8 根本還不存在。不要把時間花在「換模型」上。 另外請注意：根因目前是強推論，尚未被時間證實 —— 八月的記憶體歷史已因保留期過短而消失。

你到場時，機器是哪一種狀態？

這是整份文件的分岔點。先確定你在哪一欄，再往下做。

情境 A

機器正凍著

照順序做。不要一開始就拔電。

  1. 先從別台電腦試 ssh

    機器可能只是卡住，不是全死。

    ssh spark-66b8@100.77.199.82  # Tailscale

  2. 接得上就不要重開，直接救記憶體

    sudo systemctl stop ollama
free -g
tail -30 /var/log/freeze-sampler.log

    停掉最可能的兇手，看 available 有沒有回來。

  3. 接不上 → 用 SysRq 安全重開

    本機鍵盤，按住 Alt+SysRq 不放，依序按下列字母，每個間隔 2 秒：

    Ssync 落盤
    U重掛為唯讀
    B重開機

    這台只開了 S U B（kernel.sysrq=176）。 Alt+SysRq+F 手動 OOM kill 不能用。 硬斷電有檔案系統損毀風險，SUB 沒有。

  4. SysRq 也沒反應 → 才長按電源鍵

    按下去之前先記下這三件事 —— log 裡不會有，只有你知道：

    ① 當時誰在做什麼？
    ② open-webui 有沒有在載模型？哪一顆？
    ③ 螢幕上最後顯示什麼？

    重開後把這三點補進 sop_dgx_freeze.md 第 8 節追蹤表。

情境 B

到場時已經重開過了

證據還在，但你得知道去哪撈。

  1. 先跑全套追查

    bash ~/wchien/HermesAgent_Setup/postmortem_freeze.sh

    證據在「上一個 boot」，不在你現在這個 boot。 腳本預設就讀 -b -1。不要自己去翻當前 boot 然後說「什麼都沒有」—— 這是查這類問題最常見的錯誤。

    要查更早的：postmortem_freeze.sh -2

  2. 如果只來得及看一個東西，看這個

    tail -50 /var/log/freeze-sampler.log

    這個檔案每 20 秒寫一行，每行寫完立刻 fsync 落盤， 所以硬鎖死也不會遺失（journald 會遺失最後幾秒到幾分鐘）。 

    2026-09-10T21:50:35 avail=55811MiB/122570MiB(45%)
gpu=53019MiB ollama=[-] top=[VLLM::EngineCor:2.9G ...]

  3. 照下面那張表判讀

    重點看兩個地方：取樣器的 avail 走勢， 以及 postmortem 第 4 段 earlyoom 有沒有出手。

    看到 earlyoom ... ollama 是好消息 —— 代表保護機制生效，只有 ollama 被殺，機器沒死。

判讀表

看到什麼 → 代表什麼 → 怎麼做。

你看到意思動作
avail 一路掉到近 0 記憶體耗盡確認，診斷正確 看同一行的 ollama=[...] 是哪顆模型，回報並考慮刪除
第 4 段有 earlyoom 殺 ollama 保護生效，機器其實沒死 正常結果，不用改設定。查一下是誰觸發載入
earlyoom 沒動，但 avail 見底 記憶體確實耗盡，但保護沒趕上 把門檻調高：sudo sed -i 's/-m 10 -s 10/-m 15 -s 15/' /etc/default/earlyoom 後重啟
avail 一直 > 30000 MiB 卻死機 不是記憶體問題，本文的診斷錯了 改查 GPU（Xid/NVRM）、電源、散熱。見 SOP 情況 C
取樣器檔案不存在 證據保存機制沒裝成功 sudo bash setup_freeze_evidence.sh

重要檔案

全部在 ~/wchien/HermesAgent_Setup/。前兩個是你真正會用到的。

檔案用途什麼時候用
sop_dgx_freeze.md完整 SOP，含判讀決策樹與事前佈署想搞懂細節
postmortem_freeze.sh死機後全套追查，9 個面向重開機後第一件事
handoff_freeze_oncall.md本頁的純文字版機器上查看時
fix_dgx_freeze.sh根因修復：刪大模型、ollama 加上限、裝 earlyoom重灌／還原後重跑
fix_earlyoom_args.shearlyoom 參數修正保護參數掉了時
setup_freeze_evidence.sh佈署證據保存：journald 10s sync + 取樣器重灌／還原後重跑
freeze_sampler.sh20 秒取樣器本體由 service 呼叫，不用手動跑

產生的證據檔：

路徑說明
/var/log/freeze-sampler.log最可靠 —— 每行已 fsync，20 秒間隔，保留 30 天
/var/log/sysstat/saYYYYMMDD10 分鐘間隔記憶體歷史，保留 30 天（注意是長檔名，不是 saDD）
journalctl -b -1系統 log，最多缺最後 10 秒

平時健康檢查

30 秒，每週跑一次就好。

free -g                                      # available 應 > 40 GB
nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv
                                             # 只應有 vLLM ~53000 MiB
ollama ps                                    # 平時應為空
systemctl is-active earlyoom freeze-sampler ollama
ps -eo args | grep '[e]arlyoom'              # 必須含 --avoid 和 --prefer
tail -3 /var/log/freeze-sampler.log          # 取樣器還活著嗎

最後那行 ps 必須看到 --avoid 和 --prefer。 如果只有 -r 3600，代表保護失效，而且 earlyoom 反而可能去殺 vLLM —— 立刻跑 sudo bash fix_earlyoom_args.sh。

不要做這些

每一條都有人踩過，或差點踩到。

✕

不要為了「更穩」把 vLLM 換成官方 FP8

FP8 佔 88 GB，只剩 31 GB 餘裕，在這個根因下反而更容易死機。目前的 NVFP4 佔 52.9 GB 是最安全的。

✕

不要拉超過 40 GB 的 ollama 模型

規則：新模型 + 53 GB（vLLM）+ 11 GB（系統）必須 < 110 GB。OLLAMA_GPU_OVERHEAD 會擋，但別依賴它。

✕

不要升級 vLLM 容器到 26.06 以上

26.06/26.07 需要 driver 610.43、26.08 需要 615.65，本機是 580.126.09，而 DGX OTA 7.4.0 仍只帶 580。升上去開不起來。

✕

不要裝 Ubuntu 通用 nvidia driver

nvidia-driver-595/610-open 會覆蓋 DGX 專用平台模組，重開後 GPU 可能無法列舉。只能走 DGX OTA。

✕

不要直接拔電

先試 SysRq S → U → B。硬斷電有檔案系統損毀風險。

交接時尚未完成：setup_freeze_evidence.sh 當時還在等 sudo 密碼。 接手前請先確認 systemctl is-active freeze-sampler 回 active、 tail -3 /var/log/freeze-sampler.log 有近期時間戳、 且 /etc/systemd/journald.conf.d/10-freeze-evidence.conf 含 SyncIntervalSec=10s。 任一項不符就重跑該腳本。
