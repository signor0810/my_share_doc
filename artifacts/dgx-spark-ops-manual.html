記憶體預算（121 GiB 可用）

vLLM 固定佔約 53 GB（--gpu-memory-utilization 0.45），系統與服務約 11 GB，平時剩 55–60 GB 給其他同事使用。規則：新模型 + 53 GB + 11 GB < 110 GB。不要拉超過 40 GB 的 ollama 模型。

2. 兩個管理 agent

dgx-agent（Linux，跑在 DGX 上）

  • 模型換版：相容性檢查、swap、驗收、回退
  • Hermes 升級：pin 到 release tag
  • 健康檢查：ops/dgx_health.sh
  • 當機後的鑑識與 SOP 維護
  • cron 任務是否成功

工作目錄 ~/wchien/HermesAgent_Setup/，角色寫在 ops/CLAUDE.md。

win-agent（Windows，orchestrator）

  • 重建 Hermes Desktop，版本與 DGX 相同
  • 驗證 Windows → :8000 與 :9119 的連線
  • 指派 agy 做網路研究、整理檔案
  • 維護這份文件

工作目錄 D:\DATA_google_dirve\0_DGX_Spark，規則寫在 CLAUDE.md，結構見第 8 節。

鐵則：遠端時絕對不重開、不關機。需要重開的修正一律寫進現場 SOP，由現場同事執行。檔案只歸檔不刪除：可刪的放 archive_to_delete/，值得參考的放 archive/，由人確認後再刪。

3. 檢查更新（每次更新前先跑）

在 Windows 的 0_DGX_Spark 資料夾開 Claude，說「根據 DGX_Agent_Architecture.html 檢查 Hermes Agent 和本地模型的更新」。它會照 CLAUDE.md 的清單跑下面七步。前六步都只讀不改；第 7 步交出報告，你一次決定完之後才動手。

步驟檢查什麼怎麼查
1. 前置dgx-agent 在線、ssh 通ListAgents 看得到 dgx-agent；不在線就在 DGX 開 Claude，執行 /remote-control dgx-agent
2. 現況兩端版本、模型、驅動、健康DGX：hermes --version、vLLM 模型 root、nvidia-smi、/etc/dgx-release、ops/dgx_health.sh。Windows：Desktop 的 tag、Node ≥ 22.22
3. Hermes有沒有新的 release taggit ls-remote --tags origin 'v20*'，比對目前 tag，讀 release notes 裡設定、gateway、desktop、cron 的變更
4. 驅動與容器驅動到 610 以上了嗎到了就能用 NGC 26.06+ 容器，也就能換官方 nvidia/Qwen3.8-27B-NVFP4
5. 模型有沒有新的 Qwen 或官方量化版Hugging Face API；逐一檢查權重大小（vLLM ≤ 約 53 GB）、model card 要求的 vLLM 版本、lm_head 是否量化
6. 排程定期任務都成功嗎hermes cron list，每個 last run 都要是 ok
7. 報告一張表：現況、可用版本、相容與否、建議需要你決定的事一次問完；之後 DGX 端交給 dgx-agent，Windows 端跑 scripts\hermes_update_desktop.ps1 -Tag <tag>，最後更新本手冊
你要在場的時刻：回答第 7 步的決策；DGX 端真正升級前，在 dgx-agent 那邊核准一次；Windows Desktop 重建完後開一次確認連得上。

4. 下一次模型更新

先查相容性鏈，四環都通過才動手。2026-10-03 換官方 NVFP4 失敗，就是卡在第 3 環。

環節怎麼查目前（2026-10-03）
1. 主機驅動nvidia-smi、/etc/dgx-release580.178.04（OTA 7.6.0）。只能透過 DGX OTA 升級，不要裝 Ubuntu 的 nvidia-driver-6xx。
2. NGC vLLM 容器NGC tag 要求的最低驅動26.04 / 26.05 可用；26.06 以後需要 ≥610
3. vLLM 版本model card 寫的 vLLM 版本0.19（26.04）
4. 量化格式hf_quant_config.json，是否量化 lm_head官方 nvidia/Qwen3.8-27B-NVFP4 需要 nightly vLLM 不相容
  1. 確認權重大小，並符合記憶體預算規則。
  2. 先下載權重（不影響服務），再寫 swap 腳本。舊容器一律改名保留，不要刪除。
  3. 啟動參數一定要帶 --api-key，因為 :8000 也綁在公網 IP 上。保留 --reasoning-parser qwen3 和 --tool-call-parser qwen3_xml。
  4. 跑 verify_backend.sh（需設 VLLM_API_KEY），檢查別名、算術、</think> 洩漏、tool call JSON、prefix cache、MTP。
  5. 驗收 FAIL 就跑 rollback.sh。冷啟動需要 3–6 分鐘，這段時間 Hermes 會改走 fallback。
  6. 從 Windows 端驗證 /v1/models 與一次 chat completion。
  7. 穩定一週後，再把舊權重移到「可回收清單」。
現行決策：維持社群版 sakamakismile/Qwen3.8-27B-MTP-NVFP4。等 DGX OTA 帶來 ≥610 的驅動後，改用 26.06 以上的容器，再換官方 NVFP4。換模型的腳本已修補為會沿用 api-key。

5. 下一次 Hermes Agent 更新

兩端一律 pin 在同一個 release tag。main 是開發分支，已比 v0.21.5 多出六千多個 commit，不要直接 hermes update。

  1. 查最新 release：git fetch --tags; git tag --sort=-creatordate | grep '^v20' | head。tag 為日期格式，例如 v2026.9.24 = v0.21.5。
  2. DGX 端備份（playbook §0②），記下 HEAD；hermes update --backup 另外會做 zip。
  3. DGX 端 checkout tag，依該 tag 的安裝流程重裝依賴、build web UI、hermes config migrate。
  4. systemctl --user restart hermes-gateway-qwen38fp4 hermes-dashboard。
  5. 驗收：hermes --version、hermes cron list、Discord、dashboard /api/status 回報 auth_required: true。
  6. Windows 端：powershell -ExecutionPolicy Bypass -File scripts\hermes_update_desktop.ps1 -Tag v2026.9.24（log 在 logs\）。需要 Node ≥ 22.22，舊 build 會保留為 win-unpacked.bak。
  7. 開啟 Desktop。若出現「Remote gateway sign-in required」，用 hermes 帳號登入，profile 選 qwen38fp4。

回退：DGX 端 git checkout <舊 HEAD> 加 hermes import <pre-update zip>；Windows 端把 win-unpacked.bak 改回原名。

6. 當機（整機凍結）

時間當下狀態判讀
2026-09-26 03:56:27avail 60 GB（49%）、GPU 53.6 GB、ollama 空、閒置非記憶體
2026-09-29 09:12:46avail 57.7 GB（47%）、GPU 52.6 GB、開機後 29 分鐘非記憶體
9/29 19:37、9/30、10/2journal 中有 systemd-shutdown正常關機

9/10 的「ollama 吃光記憶體」推論無法解釋這兩次：當時記憶體還有一半空著，也沒有 OOM、Xid、thermal 或 panic。剩下的候選原因是韌體或驅動層（10/2 的 OTA 已更新）、電源控制器。外部報告提到 GB10 電源 PD 控制器保護，但多數發生在高負載時，與我們的閒置凍結不完全吻合，尚未證實。

現場同事可以做的（需要人在現場）

  1. 凍結當下：拍螢幕、電源燈、風扇是否在轉；先從別台電腦試 ssh。
  2. 依序按 Alt+SysRq+S、U、B，不行才長按電源鍵。
  3. 拔電源 60 秒（cold drain）再開機，讓電源控制器重置。
  4. 開機後跑 bash ~/wchien/HermesAgent_Setup/scripts/postmortem_freeze.sh，它讀的是上一個 boot。
  5. 維護時段（有人在場）再開：kdump（crashkernel）、kernel.softlockup_panic=1、硬體 watchdog RuntimeWatchdogSec、fwupdmgr 韌體更新、partnerdiag --field PowerStress。

完整版：~/wchien/HermesAgent_Setup/runbooks/handoff_freeze_oncall.md（現場濃縮版）、runbooks/sop_dgx_freeze.md（完整版）。證據收集設定：scripts/setup_freeze_evidence.sh（需 sudo）。
