§ 0

案例發生了什麼

去掉修飾的版本。三輪，各否證一個結構假設。

第一輪
機械式兩層檢索模板，搜「關於 MHS 的新聞」
8 條，多為媒體轉述。Judge 依 65 分線砍掉 3 條。產出等於一份報導彙整。
第二輪
改為假設驅動，搜「誰出貨了程式碼與介面」
6 條，硬度大幅提升。撈到 Qwen 倉庫 —— 本期最有價值的一條。
第三輪
orchestrator 逐條追問查證
撤回 2 條、降級 2 條。挑戰 4 條，命中率 50%。
關鍵觀察

第二輪撈到的 Qwen 倉庫，第一輪的方法論永遠不可能找到 —— 因為沒有人會為一行 changelog 寫新聞。

第一輪搜的是「關於它的報導」，第二輪搜的是「它被使用的痕跡」。這是兩種不同的東西，不是同一件事的粗細差別。

§ 1

管線不是線性的，是兩個迴圈

實跑用了三輪，而那三輪不是「重試」—— 它們的觸發條件、處置方式、終止條件全都不同。

方向迴圈 ◀ 回 ② 換證據類別
②Hypothesize
→
③Probe
→
④Assay
查證迴圈 ◀ 有撤回則回 ④ 重排
⑤Challenge
→
⑥Compose
→
⑦Deliver

方向迴圈的觸發條件是「證據硬度不足」，處置是換證據類別重新假設。查證迴圈的觸發條件是「有宣稱該被挑戰」，處置是逐條追問，結果可能是撤回。

v0.2 錯在哪

v0.2 只有一個「覆蓋率熔斷 → 放寬查詢重試」。但方向錯的時候，放寬查詢只會撈到更多同類雜訊。

所以 v2 把方向迴圈的觸發條件寫死，不靠感覺：若排序後最高分那批的 evidence_type 仍全為 media，代表只撈到「別人怎麼說」、沒撈到「發生了什麼」→ 強制回 ② 換方向。第一輪正好符合此條件，但當時沒有這個判準，所以是靠專案擁有者指正才轉向。

§ 2

證據類別決定查詢，不只決定分數

這是 v0.2 最深的錯誤。它把來源品質當成評分階段的事，檢索時對所有來源用同一組關鍵詞。

不同證據類別要用完全不同的查詢才找得到
要找的東西有效查詢的形狀用「主題名 + 新聞」找得到嗎
一行 changelogsite:github.com + 倉庫名 + 檔案路徑找不到
廠商支援聲明site:<vendor> + developer / release notes幾乎找不到
標準組織表態site:<org> + 主題名（預期命中 0）找不到
徵才需求職缺平台 + 技能名找不到
媒體報導主題名 + 一般查詢找得到

所以順序必須反轉：先選證據類別，再由類別導出查詢。「先搜尋，再按來源品質評分」這個順序注定只會撈到最容易被搜到的那一類 —— 也就是最弱的那一類。

2.1新增 ② Hypothesize，產出 evidence_plan.json

{
  "hypothesis": "若 MHS 的採用是真的，硬證據會是有人出貨了驅動或介面",
  "evidence_classes": [
    { "class": "code", "rank": 1,
      "queries": ["site:github.com \"Model Hardware Standard\"", "…"],
      "must_capture": ["star 數", "最後 commit 日期", "含 MHS 的實際檔案路徑"] },
    { "class": "standards_body", "rank": 3,
      "queries": ["site:sila-standard.org Anthropic"],
      "expect_zero": true, "zero_is_signal": true }
  ],
  "domain_judgement": "既有標準為 SiLA 2 與 OPC UA LADS；共存或取代決定投資論述",
  "agent_proposed": []
}

must_capture 是關鍵欄位：類別特有的驗證欄位必須在檢索時一併取回，不能事後補。實跑中 agy 兩次漏掉 code 類的最後 commit 日期 —— 而那個欄位正是區分「真的在做」與「發了就沒動」的唯一依據。

domain_judgement 是 orchestrator 必須貢獻的領域判斷。agent 不被告知前，不會自己想到既有標準的存在。

§ 3

過濾與查證反向移動

v0.2 的 Judge 同時負責「這條重要嗎」與「這條可信嗎」。兩者的失敗模式相反。

核心原則

供給稀缺時，過濾要變鬆，查證要變緊。

稀缺時每條候選的邊際價值高（不該砍），但佔比權重也高 —— 一條假的在 8 條裡的破壞力，遠大於在 80 條裡。v0.2 把兩者綁在同一個 65 分門檻上，鬆緊只能同向動。必須拆開。

同一套管線，兩套參數。判準是候選數，不是主題類型
稀缺 · < 15（新主題常態）豐沛 · > 40（高流量主題）
過濾排序全收，只剔低地板（約 40）入選線 75，強化冗餘懲罰
查證逐條挑戰（可負擔）抽樣挑戰 + 要求多源互證
證據類別盡量拓寬，納入弱訊號收窄到最硬的兩三類
查無本身是交付物通常無意義
主要風險虛構內容混入真訊號被雜訊淹沒
§ 4

真正的稀缺資源是「可被挑戰的宣稱數」

v0.2 花整節算 token 預算，結論是「成本從來不是約束」—— 然後轉頭把 context 當約束，也錯。

實跑的真實瓶頸：第三輪挑戰了 4 條，2 條被撤回，命中率 50%。決定產出品質的不是候選數、不是 token、不是成本，而是一期之內有多少宣稱真的被挑戰過。

目標函數改寫

最大化的不是「收錄條目數」，是經得起挑戰的宣稱數。

寧可 5 條被逐一挑戰過的卡片，不要 15 條沒人查過的卡片。稀缺主題下兩者不衝突 —— 條目本來就少，那正是該逐條挑戰的理由。

4.1挑戰預算的優先序

  1. 最印證 orchestrator 假設的那一條
    實跑中被撤回的 404 文章，正是最完美印證假設的那條。harnessrouter.ai 提出的分層框架與 orchestrator 前一輪的推理完全一致 —— 正因如此它才顯得可信，而它的網址實測是 404。
  2. 會被引用為數字的宣稱
    幻覺最常出現在具體數值。
  3. URL 未被開啟驗證過的
    harnessrouter 那條實測 404 才現形。
  4. 日期與事件順序可交叉檢查的
    OPC Foundation 那條靠「頁面早於事件兩天」拆穿。
  5. 高分但低 Auth 的
    Tecan 那條：Dec 高、Auth 僅 20。
本案最反直覺的發現

最可能是虛構的，是最完美印證你假設的那一條。該懷疑的不是那個來源，是你想採信它的衝動。

這不是通則的老話。它是實跑中真的發生過一次的事。

4.2Challenge 的三種結論

結論處置
survived維持分數與 verification 等級
downgradedAuth 下調，verification 降為 unverified_claim，在卡片內明講來源性質
retracted移出本期，但在 TL;DR 明示本期撤回了幾條

撤回必須對讀者可見。實跑的 TL;DR 第三行就是「本期撤回兩條」—— 這比假裝它們從未存在更有情報價值，也讓讀者知道這份簡報被挑戰過。

§ 5

「查無」是可交付的產出

v0.2 只有 no_news（整期沒東西）這一種對「沒有」的處理。

實跑產出兩個高價值的「沒有」：

  • SiLA 2 與 OPC UA LADS 查無任何 MHS 表態 → 成為本期第 4 高分卡片（78.25）。這是後續最值得盯的單一訊號：任一組織的首次表態，價值高於任何媒體報導。
  • 一個 0 star 的垃圾倉庫 README 寫著 「目前並無公開的 MHS 規格」 → 解釋了為何看不到廠商級實作。弱來源裡的硬事實。

查無必須是 Probe 階段的一等公民輸出：對錨定來源的零命中要被記錄、被解釋、被評分，而不是靜默丟棄。

§ 6

提案權與決定權分離

orchestrator 一度把「該往哪裡找」外包給 agent（錯），被指正後又過度收回把 agent 當純執行工具（也錯）。

提案權決定權
orchestrator有有
agent有無

agent 比 orchestrator 多跑過該主題的實際檢索，知道哪裡有料、哪裡是死路 —— 那是 orchestrator 靠推理拿不到的實地經驗。每輪 dispatch 的最後一段一律要求 agent 提 2–3 個新方向，附理由與具體查詢式；是否採納由 orchestrator 決定。

§ 7

刪掉什麼

架構提煉的一半工作是刪除。以下 v0.2 設計正式廢止。

  • 固定 65 分入選線隱含「候選供給充足」，新主題不成立。改為 regime 決定的排序取前 N + 低地板
  • 「一手／二手文獻」的來源分級太粗，且無法導出查詢。由 evidence_type 取代
  • 單次 Harvest由方向迴圈取代
  • Judge 兼做可信度判斷拆出 ⑤ Challenge。兩者失敗模式相反，稀缺時調整方向也相反
  • 覆蓋率熔斷 → 放寬查詢重試方向錯時放寬只會撈到更多同類雜訊。改為觸發方向迴圈
  • token 預算表作為主要約束真正的約束是挑戰預算。token 表降級為附註
  • Tier-2 固定三面向模板技術指標／供應鏈／競品綁定技術主題。由 evidence_plan 的類別查詢取代
§ 8

不變的部分

經實跑驗證有效，不動。

  • §A 範疇契約 —— exclude 與 uncertain 仍是最有價值的欄位。唯一例外：新主題首期的 exclude 會誤殺唯一的一手來源（官方發布公告），需在 ② Hypothesize 階段明確豁免。
  • §G 防線 1、2（無出處即拒收、量測條件強制）—— 實跑中 Validate 零拒收，因為卡片是照規則寫的。這證明規則可遵循，不是空話。
  • §L 交付層 —— render.py 四條禁令、Artifact 與 Gmail 分流、send_message(draftId) 閉環、寄出後才寫 state。全部照設計運作。
  • §H.5 unverified_premise —— 實跑未觸發（前提由專案擁有者確認），但缺口是真的。
§G 防線 3 · 發報前人工復核門

這道門是整個架構最高價值的元件，不是行政程序。

理由不是設計得好，是實跑證據：專案擁有者這一輪的三次指正，全部發生在那道門之前。不過濾、不偵測、不查證 —— 那道門攔下的東西比任何自動機制都多。
