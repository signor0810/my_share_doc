§ A

泛用化的關鍵不是「更多來源」，是「範疇契約」

一換主題就全廢的來源矩陣，換成一份每期都被遵守的契約。

PLAN.md 把來源矩陣寫死 —— SPIE、ASML、IEEE Xplore。那套東西一換主題就全廢。

泛用引擎不能有固定來源清單，也不能有固定過濾規則。但「任何主題」的過濾器本來就無法預先定義 —— grill 就是範疇被定義的那一刻。

使用者給一個粗糙主題，系統把他問到吐出三件事：精確問題、語境與程度、收錄邊界。這三件事凝結成 brief.json。之後的搜尋、過濾、寫作全部只服從這份契約。

來源清單改由 agy 在 Discover 階段現場探勘，快取進該主題的狀態檔 —— 這就是來源矩陣的泛用化版本。

§ B

管線：判斷與機械分離

分界線按「操作」畫，不按「階段」畫 —— v0.1 畫粗了。

①Grill 人機對話：問出確切問題、align context、釐清範疇 brief.json
②Discover agy 搜尋：探勘權威來源，萃取可執行的檢索運算式 sources.json
③Harvest agy 搜尋（主引擎）：兩層檢索 + 微摘要萃取 nuggets.json
③.5Prefilter 規則過濾 + 去重，零 token、可重現 filtered.json
④Judge 對照契約做四維評分（評微摘要，不評標題） candidates.json
⑤Compose 分析 + 跨源合成 + 對抗性查核 issue.json
⑤.5Validate schema 校驗 + 無出處即拒收 issue.json ✓
⑥Deliver render.py → Artifact 頁 → Gmail 輕量信 https:// 連結

§ C

Grill Gate

一輪批次問完，不做來回盤問。這是省 token 的設計決策，不只是體貼使用者。

五類必問 — 只問會改變產出的問題
類別要逼出什麼問不出來的代價
目標
purpose		你要這份簡報去做什麼決定？寫成無用的百科摘要
決策異動點
delta ‧ NEW		發生何種具體指標變化，你才會改變既有決策或行動？產出「發生了什麼事」而非「這件事對你的淨衝擊」
程度
level		L1 外行 / L2 入門 / L3 從業者 / L4 專家 / L5 研究前沿術語密度全錯，讀不下去或太淺
邊界
scope		明確的 in／out 清單③.5 無法過濾，垃圾進垃圾出
既有認知

C.2決策異動點是反制「無聊的平均值」的主要武器agy

purpose 必須被逼問到可操作的門檻形式 —— 例：「若 High-NA 良率數據低於 X，我就改變對 A14 時程的判斷」。⑤ Compose 被要求只寫對這些門檻的淨衝擊，不寫事件敘述。這是把 §A.1 的死穴反轉成產品優勢的機制。

C.3自動注入的硬負向過濾

Grill 階段由系統自動注入預設黑名單，不需使用者自己想。可覆寫，但預設開啟。

  • 無實質資料支撐的公關稿發布平台（PR Newswire、Business Wire 等）
  • 缺乏第一手數據的彙編盤點文、內容農場
  • 純轉載、無新增分析者

C.4程度旋鈕控制的四件事

  • 術語是否附解釋
  • TL;DR 長度
  • 是否收錄一次文獻 (primary literature)
  • 卡片的推測性上限 —— L1 禁止推測；L5 允許明確標記的前瞻判斷

known 欄位有雙重用途：既是過濾器（別再講一遍），也是彈藥 —— 使用者寫下的 uncertain 正是 ③ Harvest 該去找反證的地方，也是 ④ Judge「決策攻擊力」的評分基準。

§ D

資料契約

四份 JSON。exclude、uncertain、delta_triggers 是 PLAN.md 完全沒有的三欄，也是最有價值的三欄。

brief.json — 範疇契約 
{
  "topic": "…",
  "core_question": "一句話，可被回答的",
  "level": "L3",
  "purpose": "decision | learning | monitoring",
  "delta_triggers": ["若 X 指標跨過 Y，我會改變 Z 決策"],
  "scope": { "include": ["…"], "exclude": ["…"], "sections": ["…"] },
  "known":     ["讀者已掌握，勿重述"],
  "uncertain": ["讀者沒把握 → Harvest 優先攻擊、Judge 優先給分"],
  "sources":   { "authoritative": [], "banned": [] },
  "hard_filters": { "pr_wire": true, "listicle": true, "pure_syndication": true },
  "cadence": "weekly | oneshot",
  "skip_empty": false
}

注意：seen_ids 不放在 brief 裡（v0.1 的錯誤）。跨期去重狀態移到 state.json，避免數百個 id 污染 orchestrator context。hermes

nuggets.json — ③ Harvest 輸出的微摘要

由抓取子 agent 在它自己的 context 內把每篇候選壓成約 80 字結構化微摘要。

{ "id": "…", "title": "…",
  "core_claim": "一至兩句具體技術或指標異動",
  "metric_delta": "量化指標或監管狀態變化",
  "source_domain": "…", "url": "…", "date": "…",
  "facet": "A | B | C", "tier": 1 }
sources.json — ② Discover 輸出，含可執行運算式

不只記來源名稱，必須萃取可執行的檢索運算式。

{ "anchors": [
    { "name": "ASML IR", "operator": "site:asml.com/en/investors", "weight": "primary" },
    { "name": "arXiv",   "operator": "site:arxiv.org",             "weight": "primary" }
  ],
  "discovered_at": "2026-09-25", "hit_rates": {} }
state.json — 跨期狀態，滾動保留最近 8 期 
{ "topic": "…",
  "issues": [ { "n": 1, "date": "2026-09-25", "status": "normal",
                "seen": ["正規化 URL"], "fingerprints": ["標題 SimHash"] } ],
  "url_overrides": [],
  "queries_log": [ { "issue": 1, "query": "…", "facet": "A", "hits": 12 } ] }

queries_log 同時服務可重現性：每期實際跑過的 query 逐字留存，重跑可比對覆蓋率差異。

§ E

交付與 token 預算

重內容走 Artifact，輕通知走 Gmail —— 這個分工讓 Gmail 的 CSS 閹割實質不構成問題。

render.py 把已驗證的 issue.json 灌進 HTML 模板，發布成 Artifact（真實 https:// 網址，跨裝置可點，支援表格、摺疊、深色模式），Gmail 只收一封輕量信：TL;DR 三行 + 連結。

寄送前一律先給專案擁有者確認，不自動發。

E.1Gmail 端硬限制agy 查核

  • HTML 信件 102 KB 上限，超過顯示 [Message clipped]
  • 禁止外部樣式表；<style> 區塊行動端常被剝除 → 一律 100% 行內樣式
  • 不支援 <details>／<summary>、不支援 CSS Grid 與多數 Flexbox 子屬性、封鎖 JavaScript
  • 行動端強制暗色反轉 → 色值用 #rrggbb，不用 rgba()

因為輕量信只有三行 TL;DR 加一個連結，上述限制實質不構成問題 —— 這正是內容與通知分流的價值。Artifact 端則受嚴格 CSP：禁止外部 CDN 腳本與樣式表，資源需內嵌或 Base64（Google Fonts 是唯一例外的字型來源）。

E.2預算修正hermes

v0.1 把 ① Grill 算進每期預算是錯的（那是首跑成本），且 ⑤ Compose 低估 —— 20 張卡片的結構化輸出約 4k，加上輸入約 2k，實際 6k 而非 4k。

結論

成本從來不是約束，orchestrator context 才是。「大量內容永不進 orchestrator context」這條鐵律需要機制，否則是空話 —— 三條執行方式：子 agent 回覆 10 行上限寫進 dispatch prompt 的硬規則；任一階段輸入超預算即改丟檔路徑不硬塞；每階段產出物落盤，重跑 ④⑤ 直接讀檔不重新生成。

§ F

Judge：四維契約評分

廢除「讓 LLM 憑感覺盲選標題」。總分 100，入選線 65。agy

相關度 Rel
權重 0.25

與 core_question、scope.include 的語意對齊程度。

資訊增量 Nov
權重 0.30

與 known 及本期已入選項目的語意距離。

命中 known 者直接歸零
來源權威 Auth
權重 0.20

一次文獻（論文／專利／監管備案／官方財報）最高；頂級垂直分析次之；綜合新聞轉載低；農場文歸零。

決策攻擊力 Dec
權重 0.25

是否證實或證偽 uncertain 與 delta_triggers 條目。

泛泛提及者極低分

權重視為可調參數，不是精確科學 —— LLM 指派的分數本身有雜訊，過度精確的加權是假精確。四個維度的存在，加上「Nov 歸零」與「Dec 主導」兩條硬規則，才是真正起作用的部分。這讓契約真正驅動評分，而不是當裝飾。

理論依據：Nov 維度來自 MMR（Carbonell & Goldstein, SIGIR 1998）對「相關性 vs 新穎性」的顯式權衡，以及貝氏驚奇度 —— 重要性可客觀定義為新資訊對先驗知識造成的信念位移。事件再大，若讀者早已知道，資訊增量為零。這正是 known 欄位在評分裡的數學意義。

F.1為什麼必須評微摘要而非標題

v0.1 為省 token 規定 Judge 只看 30 條標題。這有致命盲區：科技與產業新聞標題充斥點擊誘餌與誇大公關詞彙，只看標題無法判斷是否回答了 uncertain，也無法分辨是否為空洞公關稿。結果是 Judge 選中華而不實的標題，⑤ 調閱全文才發現內容無物 —— 既浪費 token 又劣化品質。

微摘要方案在子 agent 的 context 內完成壓縮，不佔 orchestrator 額度。30 條僅約 2.5k token —— 比純標題方案更省，也更準。

§ H

空期是合法狀態，不是管線故障

情報工作的標準準則：確認沒有重大變化，本身就是高價值情報。

強制每期都要有「重大進展」，是自動情報系統產生幻覺、進而被退訂的主要原因。兩位評審都獨立指出 v0.1 沒定義失敗模式。

狀態觸發條件fallback 行為
normal通過入選線者 ≥ 2正常流程
no_news放寬 query 重試一次後仍 0 命中渲染「本期無實質進展」頁，附 3 條低於門檻的邊緣觀察；嚴禁塞入超界內容；下期自動觸發 ② 重新探勘
all_excluded有命中但全部命中 exclude列出被排除標題與命中的 exclude 詞，讓使用者判斷邊界是否過嚴；只在下期 grill 建議放寬，絕不自動改契約
partial部分來源抓取失敗正常出刊，加「來源缺檔告知」；失敗來源寫進 source_gaps
核心原則

寧可誠實出一期「本期無實質進展」，也不為了出刊而塞入超出契約邊界的內容 —— 那會直接違反 §A「全部只服從契約」。契約是使用者自己畫的線，只有使用者能改：系統負責把「全被排除」這個訊號浮出來，不負責放寬。

空期預設仍發輕量通知，證明管線端到端跑完、排程沒斷；skip_empty: true 可關閉。

§ I

兩層檢索與三層去重

單一籠統自然語言搜尋的三個不確定性根源：SERP 動態波動、只取前 10 筆導致長尾沈沒、LLM 生成關鍵字的隨機變異。

I.1Harvest 兩層檢索agy

Tier-1 錨定確定性掃描 —— 對 sources.json 的 anchor 運算式做確定性遍歷，帶嚴格時間運算元，確保核心陣地 100% 覆蓋：

site:asml.com/en/investors after:2026-09-18

Tier-2 多面向正交探勘 —— 禁止向 agy 輸入單一籠統 prompt。由 core_question 與 uncertain 正交拆解為三組運算式：

面向 A  技術指標／架構突破
        "{實體}" (breakthrough OR benchmark OR spec) after:{date}

面向 B  產能／商業／供應鏈
        "{實體}" (capex OR yield OR delay OR contract) after:{date}

面向 C  競品／替代方案／瓶頸
        "{實體}" (vs OR alternative OR bottleneck) after:{date}

覆蓋率熔斷：若兩層去重後有效條目少於 15，自動啟動查詢放寬二次檢索。嚴禁在候選不足時強行進入 Judge。

可重現性：搜尋固定 temperature=0，每條 query 逐字記錄進 state.queries_log。某來源連續 2 期 0 命中則觸發 ② 重新探勘。hermes

I.2去重三層

層機制成本擋什麼
L1URL 正規化後比對 state.seen0 token追蹤參數（utm_*、fbclid、gclid）、AMP／m. 子網域、尾斜線、http/https 混用
L2標題 SimHash 指紋，漢明距離比對0 token通訊社通稿洗版 —— 同一篇 Reuters 稿被 50 家轉載，URL 各異，L1 完全擋不到
L3Judge prompt 加一句「標記再報導」~100 token同一事件、不同媒體、獨立採寫的語意重複
設計裁決 — 兩位評審在此衝突

agy 建議建 SQLite 加內文 SimHash 基建；hermes 主張 30 條／期的量級不值得專建語意去重管線。

採 hermes 的量級判斷，但吸收 agy 的通訊社洗版顧慮 —— SimHash 只算標題、狀態存 JSON 而非 SQLite，約 30 行程式碼即可取得 L2 的主要收益，而不引入資料庫維運成本。去重資料永不進入 LLM context。

L.2修正一：深色模式只做了一半

阻斷級

agy 只寫了 @media (prefers-color-scheme: dark)。但 Artifact 檢視器有三種狀態，不是兩種 —— 明確選擇會在根元素蓋上 data-theme，而預設的「跟隨系統」不蓋任何標記。

agy 的寫法完全忽略 data-theme，後果是：讀者在亮色系統上手動切到深色，頁面不會變。這是 Artifact 最典型的壞頁 bug。

:root { /* 完整亮色 token 組 */ }

@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) { /* 只覆寫 token */ }
}

:root[data-theme="dark"] { /* 再覆寫一次，讓切換鈕兩個方向都贏 */ }

追加兩條硬規則：body 必須從 token 明確指定 background（透明 body 會借到宿主底色，導致一個主題的文字疊在另一個主題的底上）；任何顏色都不准只定義在 media 或 [data-theme] 區塊裡。

L.3修正二：update_draft 會把 HTML 清掉

阻斷級 · 從工具規格挖出，agy 看不到

agy 的退回流程第 4 步呼叫 update_draft 原地更新草稿。工具規格的隱藏行為：若提供 body 但省略 htmlBody，既有的 HTML body 會被清除。

退回重製時必須同時傳 body 與 htmlBody，否則草稿退化成純文字，輕量信的 table 排版全毀。已寫成硬規則。

L.4修正三：往期導覽與不可變快照自相矛盾

agy 想在頁面注入 [◀ 上一期] 與「往期目錄清單」。但每期獨立網址的整個論證建立在快照不可變之上 —— 而一份會保持最新的目錄、或任何「下一期」連結，都需要回頭重新發布舊期，正好破壞不可變性。

  • 只准向後連（指向更舊的期次）—— 那些網址在渲染時已經存在
  • 禁止「下一期」連結，禁止在期次頁內放會過期的目錄
  • 若真需要會更新的總目錄，它必須是另一個常駐 Artifact

L.5修正四：「或於 Gmail 直接按傳送」是狀態漏洞

阻斷級

agy 允許擁有者直接在 Gmail 按傳送。但那樣 orchestrator 永遠不知道信寄出去了，state.json 不會記錄該期，下一期的跨期去重就從此失準。

裁決：核准只走 CLI 一條路。擁有者可以在 Gmail 裡讀草稿，但傳送動作由 orchestrator 執行 —— 因為只有它會在寄出後補寫狀態。

L.6修正五：禁用 Google Fonts 的理由是錯的

agy 稱 Artifact CSP「嚴格禁止外鏈字型」。此為錯誤 —— Google Fonts 是 Artifact CSP 唯一放行的外部主機。

它選用系統字型棧本身是安全且可接受的決定（零外部依賴、離線可讀），故保留；但理由改為「刻意選擇零外部依賴」，避免這條錯誤事實日後無謂地限制排版選擇。其餘 CSP 規範（禁外部樣式表、禁外部腳本、圖示內嵌 SVG）正確。

L.7非阻斷的改進

  • create_draft 會回傳 viewUrl —— agy 沒用到。放進 CLI 審查單，擁有者一點就進草稿，不必翻草稿匣。免費的體驗改善。
  • 102 KB 的估算方法不嚴謹（結論仍成立）：只數了 HTML 原始位元組，沒算傳輸編碼。UTF-8 中文每字 3 bytes，quoted-printable 對非 ASCII 約再膨脹 3 倍。即使取 6 KB × 3 ≈ 18 KB，距 102 KB 仍極遠 —— 結論通過，方法記錄修正。
  • 主旨行移除 emoji。主旨帶 emoji 會干擾 Gmail 搜尋與篩選器，觀感也接近行銷信。CTA 按鈕上保留無妨。
  • 色票整組是 Google Material（#1a73e8、#137333…）。功能上沒問題，但會讓 anvil 看起來像 Google 的產品。實作模板時再處理。
  • Artifact 頁面有 16 MB 上限，agy 未提及。以本專案量級不可能觸及，備記一筆。
