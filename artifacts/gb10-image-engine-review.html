01

核心判斷：統一控制平面，不必統一執行時

agy 主張「別重寫 Diffusers 引擎，留著 ComfyUI」；原計畫主張「統一到 Diffusers」。 兩邊都只對一半 —— 因為它們在爭論的是後端，而真正該統一的是前面那一層。

ComfyUI 的動態記憶體調度確實比手寫的成熟，這點 agy 說得對； 但我們那顆 Qwen-Image-Edit int8 是 diffusers 格式，搬進 ComfyUI 要重新量化， 而 FLUX.2 Klein NVFP4 反過來 diffusers 讀不了。兩個後端各有各讀得動的權重，這是事實而不是偏好。

統一這些

admission control、單一把鎖、manifest registry、能力契約、provenance、HTTP／MCP 介面

不必統一這些

誰去載權重。Diffusers 管 edit（int8 在這），ComfyUI 管 txt2img（NVFP4 在這）

換到的東西

一個服務、一份契約、一把鎖；而且不用重寫 ComfyUI 的記憶體調度器

03

十個需要改進的地方

嚴重度以「在這台機器上出事的後果」評定，不是以修起來的難度。 標「已驗證」的是我在這台上跑過指令或讀過原始碼確認的。

致命agy 發現 · 已驗證

int8 模型存成 pickle .bin，不是 safetensors

safetensors 是 mmap 零拷貝；pickle 要在系統 RAM 解包出完整緩衝區再逐一送進 GPU。 在 GB10 上 CPU RAM 與 GPU 記憶體是同一塊 128GB，這個緩衝區直接跟 vLLM 的 52GB 搶同一池。 

transformer/  diffusion_pytorch_model-0000{1,2,3}-of-00003.bin   ← 20GB pickle
text_encoder/ model.safetensors                                 ← 這個已經對了

實測撐過去了（MemAvailable 60→24GB），但沒有餘裕。而且這讓那 29GB 綁死在 torchao 0.18.0 上。

致命natolambert/dgx-spark-setup · 181★

這台的 OOM 會凍結整機，不是殺掉行程

原計畫寫「生圖 process OOM → 這個 job 失敗，可接受」—— 那是獨立顯卡的假設。 unified memory 下 GPU OOM 直接變成全系統實體記憶體耗盡，SSH 會斷，要走硬體重開。

整份計畫的風險模型建立在一個不成立的前提上，連帶影響第 5、8 條。

致命agy 發現

模型切換抖動：交錯請求會讓吞吐量趨近於零

47.9GB 上限容不下兩個模型同時常駐，計畫因此說「先卸載再載入」。 但 txt2img → edit → txt2img 這種再正常不過的序列，每個請求都要重載 170 秒。

計畫承認了「一次一個模型」的算術，卻沒處理它的後果。

嚴重agy 發現 · 部分成立

跨機的檔案路徑語意斷裂

DGX 回 /home/spark-66b8/.../out.png，遠端 Windows 上的 Claude 讀不到那個檔案。

但這條只對一半：stdio shim 跑在客戶端本機，會把 bytes 下載成本機檔再回路徑 —— 那條路徑沒問題。 真正沒解的是遠端 HTTP MCP（:8101），以及現在 i2i.py 掃 $HERMES_HOME/images/ 找上傳圖的做法 —— 那是純本機語意，跨機直接失效。

嚴重原計畫缺漏

admission control 的「檢查 → 配置」沒有原子性

兩個請求可以同時通過 mem_get_info() 檢查，然後一起開始載入 —— 正是要避免的那件事。 flock 鎖得住自己人，但「檢查」和「實際配置」之間的時間窗沒有保護。

配合第 2 條（OOM 會凍結整機），這個競態的代價是硬體重開機。

嚴重已驗證 · 仍在

ollama 還在跑，第四道防線有破口

LISTEN *:11434。統一之後這台仍有兩個會吃 GPU 的東西，而 flock 只鎖得住自己人。

計畫把它列成「需要你決定」，但沒有在架構上處理 —— 等於沒有處理。

嚴重ecarmen16/SparkyUI · 15★

torch.compile 與 Triton 在 sm_121 上不穩

SparkyUI 作者踩過：GB10 上 torch.compile() 會引發 kernel 捕獲失敗，必須停用。 另外 flash-attn 沒有 aarch64 + CUDA 13 + sm_121 的預編譯 wheel，要改用 PyTorch 原生 SDPA。

998 行計畫裡完全沒提這兩件事，但 diffusers 有些路徑會自動啟用 compile。

嚴重agy 發現 · 我原本只是承認它

venv 寄生 ComfyUI 是架構上的自相矛盾

計畫一邊說「統一離開 ComfyUI」，一邊讓引擎的 torch 透過 _inherit_comfyui.pth 指向 ComfyUI 的 site-packages。

ComfyUI-Manager 或任何人一次 pip install -U，引擎就爆。 我原本的結論是「維持繼承但記下版本」—— 那是接受風險，不是解決它。

中等原計畫缺漏

模板要當版本控制的主體，卻沒有 schema

沒有 schema 就沒有驗證，沒有驗證的「版本控制」只是檔案改名。 而模板是會從 5 個長到 50 個的東西 —— 這是最需要 schema 的一類資產。

中等原計畫缺漏

沒有測試策略，也沒有回滾的觸發條件

998 行沒有一個字講怎麼測。生圖是非確定性的，傳統 assert 用不上 —— 這需要刻意設計。

Phase 3 說舊 skill 標 deprecated 不刪，但沒說什麼情況該回去用。 沒有觸發條件的回滾計畫，實際上不會發生 —— 只會硬撐。

04

十個建議

依「投報率」排序，不是依難度。前三個做完，第 1、2、3、5 條缺陷一起消失。

最高投報一次轉檔解 #1

把 transformer 重存成 safetensors

我在這台上讀了原始碼，這條路是通的：

diffusers/quantizers/torchao/torchao_quantizer.py:442
  def supports_safetensors_serialization(self):
      if not is_torchao_version(">=", "0.16.0"):   # 我們是 0.18.0
          return False
      return True                                  # ← 支援

當初存成 .bin 應該是量化時 torchao 版本較舊。重存一次同時解掉三件事： host RAM 的反序列化衝擊、torchao 版本鎖死、以及大機率縮短那 170 秒的冷載入。

高投報需重啟 vLLMagy 找到

vLLM sleep mode 當緊急閥門

--enable-sleep-mode 加上 POST /sleep?level=1。 在 GB10 上把權重搬去 CPU RAM 不會省下實體記憶體（同一塊）， 但丟棄 KV cache 會 —— 這台 131K context 的 KV cache 約佔 36GB。

代價是休眠期間 LLM 不可用。當成「需要跑大模型生圖時的手動閥門」，不是常態。

高投報解 #5 · 防 #2

admission control 改成「保留制」而非「檢查制」

不是「檢查還有沒有 35GB」，而是「向一個中央計數器申請 35GB 額度」—— 申請成功才開始載入，行程結束時歸還。

檢查和配置之間的競態就此消失。額度表同時可以把 ollama 的用量算進去，補上第 6 條的破口。

高投報解 #3

換模型加「冷卻水位」，並提供 dry_run

切換前要求：佇列裡沒有原模型的待處理請求，且現任模型已停留超過最小時間（例如 120 秒）。 同模型的請求批次處理完再換。

搭配一個 dry_run 參數 —— 回「會用哪個模型、要不要換載、預計多久、排隊幾個」但不生圖。 約 30 tokens，讓客戶端自己決定要不要等，比讓它 timeout 好得多。

高投報joenorton/comfyui-mcp-server · 408★

MCP 回三件套，不要只回一個路徑

抄一個已經被 408 顆星驗證過的做法，不要自己發明：

{"asset_id":"ast_9a8f21",
 "asset_url":"http://spark-66b8:8100/view?id=...",
 "filename":"...png", "mime_type":"image/png",
 "width":1024, "height":1024}

return_inline_preview = False          # 預設關閉
# 開啟時才縮到 max_dim=256 且 base64 上限 100,000 字元

asset_url 讓遠端 agent 讀得到圖（解第 4 條）， 預設關閉的縮圖讓「要看圖」變成客戶端的選擇而不是強制成本。

中等lansespirit/image-gen-mcp · 68★

模板 schema 直接抄現成的

id / version（語意化版號）/ category / template（帶插值的字串）/ parameters（型別＋預設＋enum）/ metadata（建議尺寸、steps、搭配模型）。

整個模板目錄進 git，客戶端只傳 template_id 加參數字典。解第 9 條。

中等ComfyUI-Manager 慣例

LoRA manifest 用 sha256 + base_model

權重不進 git；manifest 記 {name, sha256, base_model, default_weight}。 sha256 防權重漂移，base_model 讓 registry 自動擋掉不相容的 LoRA —— 這同時就是「只收註冊過的名字」那條安全規則的落點。

中等因為 #2 才成為必要

熔斷器：逼近水位就拒絕服務

因為這台的 OOM 會凍結整機而不是殺掉行程，熔斷不是 nice-to-have。 連續 N 次逼近上限就回 503 + Retry-After，並主動卸載模型。

監看的是 torch.cuda.mem_get_info() 和 /proc/pressure/memory 的 some avg60 —— 不是 swap used（那個長期非零但無害）。

中等解 #10

Golden image 回歸測試，用感知雜湊

固定 seed + 固定模板 → 存一張基準圖 → 用 pHash 比對。 容忍浮點層級的差異，但抓得到「模型載錯」「LoRA 沒掛上」「量化壞了」這類真正的回歸。

同一套測試順便當記憶體回歸測試：每次跑完檢查 mem_get_info 有沒有回到基線。

低成本文件衛生

把 DGX-IMAGE-ENGINE.md 標為 superseded

現在 workspace 有四份文件，其中最舊那份的三個數字是錯的： fraction 0.20（實際會 OOM）、FLUX 大小（少算一半）、 「Hermes 改 base_url 就能用」（只有 deepinfra 吃 base_url，而它拒絕 img2img）。

留著不標記，遲早有人照它做。同時把環境斷言寫進 manifest：停用 torch.compile、用 SDPA 不用 flash-attn。
